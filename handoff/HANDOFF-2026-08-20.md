## 0. 先读这一节：本仓最容易犯的错

这一天里**每一个**被推翻的结论都属于同一类：**用局部事实推全局结论，而决定
适用范围的那个前提没有被记录下来**。列出来是因为你极可能重犯：

| 形态 | 实例 |
|---|---|
| 性能结论没记测试形状 | `BATCH_GQA` 被文档判"无稳定收益"，实测 qoLen=1 是 1.72x、qoLen=3 只有 1.03x |
| 从函数中间开始读 | `ForwardMultimodal` 开头有"续 prefill"守卫，漏读它就会推出"必定 500" |
| 拿不相关的样本对比 | `req#2`/`req#3` 是两个不同会话，被当成"连续两轮命中失败" |
| 没控制上下文长度就比 tok/s | IQ4_XS 被误判为"比 Q5 慢"，实为快 1.20x |
| 串行下成立的方法用在并发上 | "归属到请求窗口"在 `--batch 1` 成立，`--batch 4` 下静默给出错误答案 |
| 指标本身在撒谎 | `hits` / `L1trie` / `kv_pool` / `inflight` / `mm=0` 五个都误导过 |
| 探针自身的假阳性 | `llama-cli` 默认回显 prompt，抄写探针恒为通过 |
| 拿未核对的估算做决策 | "追赶 pass 只要 1~2 秒"，实际需要重跑 100 秒的主前向 |

**可复用的操作手法**（比记住上面这些更有用）：

1. **`grep -c` 对照法**：新增一条并行代码路径时，把原路径上的每个调用
   `grep -c` 一遍，再在新路径上数一遍。多模态路径就是这样被查出漏了
   管理器基址、decode 路由、记录钩子、hidden-state 捕获**四处**。
2. **埋点代替推断**：任何"A 是否发生"的问题，先问"有没有计数器"。没有就加。
   `mtp_steps_multimodal` 一个计数器顶得上一小时的时序分析。
3. **探针要能自证无效**：区分"模型没过"与"探针坏了"。前者 exit 1（回滚），
   后者 exit 2（**不回滚**，因为那说明你没测出来）。
4. **微基准加"等效 B/行"这一列**：立刻能回答"这个尺寸测的是带宽还是启动开销"。
5. **用"A 比 B 大多少倍"表达前，先看 B 是否离开噪声底**。

详见 `v100-perfs/docs/EXPERIENCE.md` §15.35~15.44。

## 3. 没干完的活（按价值排序）

### 3.1 【最高】工具调用块不闭合 —— z3rm 卡死的直接原因

**现象**：z3rm 的 agent 在 pane 里写 markdown 代码块而不是发工具调用，
一路循环 `gh pr view 251 → 252 → … → 258`，用户打两次"你调用工具的方法不对"
也纠正不过来。

**根因**（已定位，未修）：

```
[req 0] done: prefill 84758 tok 9.71s | decode 7883 tok in 1113.58s (7.1 tok/s)
[ToolCall] MALFORMED unterminated block (55812B)
```

模型开了 tool_call 块、生成 7883 个 token（55812 字节）后**发出 EOS 却从未闭合
该块**。它没撞 `max_tokens`（65536），是自己停的。块残缺 → 解析器退回显示
原始文本 → 用户看到 markdown。

**语法约束有一个洞：块未闭合时停止符没有被屏蔽。**
回看 `test/toolcallGrammarTest.cpp` 与
`v100-perfs/tests/toolcall_grammar_invariants.py` 的断言清单 ——
覆盖了"必填未齐时 `</function>` 不可拼"、"空值不能闭合 `</parameter>`"、
"循环起点参数名受限"，**没有一条断言"块未闭合时 EOS/停止符不可达"**。
测试覆盖了"不能提前闭合"，漏了"不能不闭合就结束"。

**修法**：在状态机处于 S2/S3/S4（块内）时，把 EOS 与所有停止符加入
blocked 黑名单，直到 `</function>` 闭合。两套测试各补一条断言：
`can_spell(块内文本, EOS) == False`。

**代价**：全部日志里 3 次 MALFORMED + 2 次 REPAIRED —— 罕见但致命，
一次浪费 18.5 分钟，之后 agent 退化成写 markdown 循环。

### 3.2 【高】MTP 对 vision 请求从未生效

**已实证**：
```
mtp_steps                    4746
mtp_steps_multimodal            0     <- 判据未满足
mtp_multimodal_prefill_done     2     <- F9 的标记确实置位
mtp_multimodal_decode_steps  1616     <- 多模态 decode 确实走了新路径
```
生产日志直说：`[Qwen3.5 MTP] not enabled: MTP cache was not seeded during prefill`

**根因**：MTP 草稿 KV 缓存在 **prefill 期播种**（文本路径用
`appendLongPrefillMtpCache` / `seedMtp`），而 `ForwardMultimodal` 从不做。
判据在 `src/models/qwen3_5.cpp:15825-15833`。

**已选定的修法（方案 a，未写）**：`ForwardFromHiddenStates` 结尾处
`hiddenStates` 已是完整的 `[1, seqLen, hidden]`（就在 `LLMSamplingBlock` 之前）。
在现有 `speculativeCaptureAllHiddenStates` 门控下做一次最终 RMSNorm +
`CopyFrom` 到 `speculativeHiddenStates`，复用为快照梯子加的 per-chunk 钩子
逐块 append。**不改变任何已有计算。**

**三条硬性约束**（都是踩出来的）：
1. 门控**复用现有标志**，不要新开 —— 否则会出现"文本开着多模态关着"的
   第五次不对称。
2. **必须走 append helper**，不要在最后做一次全量 `CopyFrom` ——
   `CopyFrom` 是覆盖不是追加，而 `expectedMtpTokens = cacheLen + preTokens -
   seqLens[0]` 要求精确匹配；对不上时 MTP 会**擦掉自己的缓存并退出**，
   表现是"有时有 MTP 有时没有"，比一直没有更难查。
3. **播种失败落回"MTP 关闭"而不是抛异常** —— `forwardLocker` 那次静默死锁
   就是异常穿过前向路径造成的。

**已排除的方案 (b)**：首次 decode 步做追赶式 MTP pass。不可行 ——
`RunMtpGreedyDraft` 消费的 `targetHiddenStates` 是主模型每个位置的 hidden
state，而"前缀命中"的定义就是这些从未被算过。追赶 pass 等于在 7 万 token 上
重跑主前向，正是刚消掉的那 100~182 秒。

**验收**：`mtp_steps_multimodal != 0`（查 `/props`，不做时序推断）。

### 3.3 【中】快照梯子（已写完未部署）

代码已在工作区（几何间距 1K/2K/4K…64K，`ForwardMultimodalWithContext` plumbing，

### 3.4 【中】184 个生产请求里有 20 个走了 MakeInput 兜底

## 4. 环境里的坑（不知道会浪费很多时间）

1. **`start_prod.sh` 不带参数默认 Q5 档**，要显式传 IQ4_XS profile。
2. **`tmux respawn-pane -k` 不带命令会重跑 pane 的原命令** ——
   之后 `send-keys` 的那行只会被打进已在运行的进程的 stdin。
   正确写法：`tmux respawn-pane -k -t <pane> "<cmd>"`。
3. **`/health` 返回 200 不等于就绪**。proxy 一起来就 200，而权重要 3~9 分钟；
   更隐蔽的是 fastllm 读完权重先放主机内存（RSS 已 20GB），
   **要到第一次真实请求才上卡**（GPU 从 724MB 跳到 22GB）。
   可靠判据只有一个：**等到新 pid + 环境变量正确 + 真发一次补全拿到 200**。
4. **omp 的 Esc**：流式中只中断当轮，非流式才 `pauseLoop`，而中断后立刻进入
   下一轮 —— "按一次等几秒再按"永远错过窗口（实测按 10 次都没成功）。
   正确手法：**0.35 秒间隔连按三次**，一组就进 `Loop paused`。
5. **后端 stdout 不在 pane 里**，在
   `v100-perfs/runtime/fastllm-native-profiles/logs/backend-PROD-cyber-*.log`。
   每个 profile 写自己的文件，固定的 `tail -f` 换模型后会永远停在旧文件上。
   用 `scripts/follow_backend_log.sh`（从 `/proc/<pid>/fd/1` 反查当前文件）。
6. **HF 上传必须 `HF_HUB_DISABLE_XET=1`**：xet 后端走 `cas-server.xethub.hf.co`
   这个**另一个域名**，经本机代理不通，表现是传到 19% 后静默卡死。
7. **`1CatVLLM` 不是 git 仓库**。`thinking_proxy.py` 这个生产入口进程的全部
   历史就是 7 个手工 `.bak-*` 文件。已放一份快照进
   `v100-perfs/deployed/thinking_proxy.py`，**改了要手动同步回去**。
8. **编译要串行**：`until ! pgrep -f "cmake --build"; do sleep 10; done`，
   `build-rw/` 是生产在用的，曾被并发编译写坏过。

## 7. 用户明确要求的两件（写在最后，优先级高）

### 7.1 chat template 要有**离线 dry-run 校验**，不许加载权重

现状是：模板解析失败只能在**推理时**发现，而那时已经加载了 16 GB 权重、
起了工作线程。而且失败是**静默降级**（退回 `MakeInput` 兜底），
服务照常返回 200，只是 prompt 用了非规范格式 —— 184 个请求里有 20 个是这样
被服务掉的，没有任何人察觉。

**要做的**：一个独立的 dry-run 工具，输入是
`chat_template.jinja` + 一组代表性 payload（纯文本 / 带 tools / 带图像 /
Anthropic 协议 / 各档 `reasoning_effort`），输出是每个 payload 的渲染结果或
解析错误。**不加载任何权重**，秒级完成。

放在 `fastllm/tools/` 下，和 `tools/prefill_dequant_bench` 同级。
它同时是 CI 门槛：换模板、换 proxy 的 payload 构造逻辑之后必须跑一遍。

payload 语料可以直接从生产日志里捞 —— `MakeInput fallback` 那 20 条就是现成的
失败样本，先让工具能复现它们，再谈修。

### 7.2 启动时要**显式报错并指出后果**

现在 `Jinja Error: expression error at end (stack=3).), using MakeInput fallback.`
这行埋在几万行日志里，而且措辞让人以为"有兜底所以没事"。

**要改成**：
- 启动时对内置/配置的 chat template 做一次解析自检，失败就在
  `[Load]` 阶段用醒目格式打出来，写清楚**后果**：
  "模板解析失败 → 所有请求将使用 MakeInput 兜底 → prompt 格式非规范 →
  工具调用与输出质量可能受影响"。
- 运行期每次触发兜底时计数并暴露到 `/props`（比如 `template_fallback_count`），
  这样"有多少请求是这样被服务的"变成查表而不是 grep 日志。
- 考虑加一个 `FASTLLM_STRICT_CHAT_TEMPLATE=1` 让解析失败直接拒绝启动 ——
  对生产环境，"用错误格式服务"往往比"不启动"更糟。

**理由**：这一天里最贵的几个问题都是同一个形态 ——
**降级路径存在、能工作、但没人知道自己在降级路径上**。
`bind error` 后握着 20GB 不服务、探针绕道代理、MTP 对 vision 从未生效、
前缀缓存 0% 命中，全都是这样。兜底本身没错，**兜底不出声才是错的**。
