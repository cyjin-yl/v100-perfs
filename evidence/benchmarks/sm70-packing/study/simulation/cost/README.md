# SM70 编译实证与打包算子的结构成本

## 结论和证据等级

这轮工作取得三项具体进展：

1. **直接使用 SM70 的 `mma.m8n8k4` 是可行的。** 本地 CUDA 12.8.93 编译结果恰好包含四条 `HMMA.884.F32.F32.STEP0…STEP3`，22 个寄存器、零 spill。因此 K=4 的候选不必被 C++ WMMA 的 K=16 接口阻挡。
2. **双侧 ternary 打包确实减少 Tensor Core 指令，但解码吃掉了相当一部分收益。** 对两份 16×16、K=32 输出，普通版本需要 64 条 HMMA；打包版本需要 32 条。但在这里的直接 global-memory 内核中，完整指令数仅从 233 条降至 214/215 条，不能从 HMMA 减半直接宣布两倍加速。
3. **找到一个具体的解码改进。** 限定数值范围后，利用 FP32 位模式可去掉所有 F2I、I2F、FRND 指令。新版本仍有 INT32 工作，也没有总指令数优势，因此它是值得实测的管线调度候选，而非已证实的加速。

证据分为：真实 CUDA 编译与 SASS；CPU 精确算术检查；标明假设的指令/字节成本模型。**这里没有 GPU 执行、时钟测量、硬件轨迹，也没有周期精确仿真。** 这些源码生成的是可用来继续试验的 SM70 对象文件。

## 1. 编译结果

工具链为 NVIDIA CUDA 12.8.93，目标 `sm_70`。使用父工作区现有的私有 SDK；它为本地 glibc 2.41 做过四条未使用 sinpi/cospi 声明的兼容修正，详见父目录 `compile-evidence/compile-check.json`。这里未修改系统头文件、驱动或远端电脑。

所有下列内核均为零 shared memory、零 stack、零 spill。表中的完整指令数是直线 warp 路径，排除了恒假启动 SHFL 和 EXIT 后的填充跳转；包含寻址、装载和存储。

| 内核 | HMMA | 完整指令 | 寄存器/线程 | warp/CTA | 资源允许的 occupancy |
|---|---:|---:|---:|---:|---:|
| 两份普通 K32，4 warp CTA | 64 | 233 | 56 | 4 | 56.25% |
| 双侧 K32，固定常数浮点解码 | 32 | 214 | 40 | 4 | 75% |
| 双侧 K32，F2I/INT/I2F 解码 | 32 | 230 | 38 | 4 | 75% |
| 双侧 K32，位模式解码 | 32 | 215 | 40 | 4 | 75% |
| 共享 B、K16，固定常数浮点解码 | 16 | 152 | 32 | 1 | 50% |
| 共享 B、K16，F2I/INT/I2F 解码 | 16 | 184 | 32 | 1 | 50% |

Occupancy 是按资源预算计算的上界，不是实测活跃度：每 SM 65,536 个 32-bit 寄存器、最多 64 warp/32 CTA，假设寄存器按每 warp 256 个分配。**一 warp 一个 CTA 会先撞上 32 CTA 限制，最多只有 50% occupancy。** 将其合成四 warp CTA 是比机械削减两三个寄存器更直接的候选改善。官方 Volta 资料给出的 SM 容量和四个 warp scheduler 与此资源模型相符。[NVIDIA Volta Tuning Guide](https://docs.nvidia.com/cuda/volta-tuning-guide/index.html)

`static-cost-results.json` 给出了所有 9 个内核的完整 opcode 分类、假设、occupancy 计算、字节模型和证据 SHA256。`compile.stderr` 是实际 ptxas 输出；`sm70-sass.txt` 是实际反汇编。

### Tensor Core 粒度

在本地生成的机器码中，一次 `wmma.mma` 16×16×16 对应 16 条 HMMA STEP；这与 Volta 原始微基准论文的反汇编一致。一 warp 每条 STEP 对应 512 个物理 FLOP；16 条合计 8,192 FLOP。本文把 FMA 计为两个 FLOP。[Jia et al., 2018，§4.3](https://arxiv.org/pdf/1804.06826)

`m8n8k4_probe.cu` 进一步确认：单条 PTX `mma.sync.aligned.m8n8k4.row.col.f32.f16.f16.f32` 生成四个 HMMA STEP。这里要注意官方定义：**一个 warp 并行计算四份 8×8×4**，并不是让全部 32 线程只计算一份 8×8。每线程持有 8 个 FP32 累加元素，输入寄存器必须采用指定 fragment 布局。该 shape 对 FP16 明确支持并针对 `sm_70` 优化。[NVIDIA PTX ISA，mma.m8n8k4](https://docs.nvidia.com/cuda/archive/11.4.0/parallel-thread-execution/index.html)

`m8n8k4-sass.txt` 是支持性编译证据。这份最小程序只验证指令能生成；还没有为它构造完整矩阵布局及硬件正确性测试。

## 2. 位模式解码：从结构反推得到的新候选

双侧 ternary、R=256、K=32 时：

```text
Z = L + 256*X + 65536*H
|L| <= 32; |X| <= 64; |H| <= 32
|Z| <= 2,113,568 < 2^22
```

传统解码先提取 H，再提取交叉项 X，最后相减得到 L。整数解码可以跳过 X：

```text
i = float_to_int(Z)
H = (i + 32768) >> 16
L = ((i + 128) & 255) - 128
```

这消除了交叉项解码，却增加了转换。真实编译结果不支持“整数一定更快”：整个内核由浮点版 214 条增加到 230 条。

更好的候选利用 FP32 在 `[2^23,2^24)` 范围内相邻整数都有连续位模式。令 `B=1.5×2^23=12,582,912`，则 `Z+B` 在这个区间内，位模式恰好为 `0x4b400000+Z`。因此可用一次 FADD、移位和掩码，得到两个结果的位模式，再用 FFMA 还原到物理值 `q_product/4`。

本地编译中，原浮点解码及 1/4 缩放共出现：

```text
32 FMUL + 16 FRND + 16 FFMA
```

位模式版本变成：

```text
8 FADD + 16 FFMA
```

F2I、I2F 和 FRND 全部消失；与此同时 INT32 操作增加。总指令数 215 条，略多于固定常数浮点版的 214 条。Volta 有独立 FP32/INT32 执行单元，调度有可能受益，但不能假设整数解码免费，也不能据静态指令数给出准确运行时间。

CPU 以 NumPy float32/int32 穷举了独立边界内所有 `(L,H,X)` 组合，集合还大于实际可达点积集合：

| q 的范围 | K | 组合数 | L 错误 | H 错误 | 最大绝对 Z |
|---|---:|---:|---:|---:|---:|
| {-1,0,1} | 32 | 545,025 | 0 | 0 | 2,113,568 |
| {-1,0,1} | 48 | 1,815,937 | 0 | 0 | 3,170,352 |
| {-3,…,3} | 4 | 772,705 | 0 | 0 | 2,377,764 |

可复跑脚本为 `validate_magic_decode.py`，结果为 `magic-decode-validation.json`。这验证的是位模式算法的 CPU 算术，不等于验证真实 Volta HMMA 的全部数值行为。

## 3. 精确域还能扩到哪里

对双侧 ternary，保持所有输入 FP16 精确、低位可分离、最高位可分离和 FP32 整数精确的充分条件是：

```text
K < R/2
K*(2*R + 1) < R^2/2
K*(R+1)^2 < 2^24
```

扫描 2 的幂 radix 后，R=256 和 R=512 都容许 K≤63；采用常规 WMMA 时，最大完整块为 K=48。R=256/K48 还能继续使用上述位模式解码。**K48 不能直接跨越两个尺度不同的标准 MX32 块。** 只有尺度可合并时才有这种减少解码频率的机会，不能改掉 MX 数据含义来换吞吐。

更有价值的另一条路线是底层 K4：对 `q∈{-3,…,3}`，**双侧 R256/K4 已经足够**。操作数最大 771，FP16 精确；`|L|,|H|≤36`、`|X|≤72`，最高位的余项 `256×72+36=18,468<32,768`。最大整数累加 `4×771²=2,377,764<2^22`，不仅 FP32 精确，还能直接使用上面的 R256 位模式解码。无需把 radix 提高到 512。

此值域覆盖 E2M1 中 `[-1.5,1.5]` 的七个数，而不限于 ternary。其代价是解码更频繁；每 warp 四个 HMMA STEP 后就要处理 256 个输出槽，性能未必合算。它是实际可编译的扩展方向，不是全范围 MXFP4 结论；窄值域 K4 的完整数值验证由相邻 numerics 实验单独报告。

## 4. 指令模型能说明什么

`analyze_cost.py` 记录了一个非常乐观的 SM 摊销下界：

```text
issue floor = warp instructions / 4 schedulers
tensor floor = HMMA steps * 512 / 1024 FLOP per SM-cycle
FP32 floor = basic FP32 instructions * 32 lanes / 64
INT32 floor = selected basic INT32 instructions * 32 lanes / 64
```

取这些 floor 的最大值仍忽略依赖、转换吞吐、load/store、缓存、共享内存、寄存器银行、调度分区与数据准备。它是资源需求的估计，**不是模拟出的 kernel latency**。示例中 4-warp baseline 的最大 floor 是 58.25 个 SM 摊销周期，固定浮点版 53.5，位模式版 53.75；这些值主要反映当前朴素实现的指令发行压力。不能把两个下界的比值解释成必然加速比。

同样，TC 理想工作量从 32 个 SM 摊销周期降到 16，只说明硬件乘加工作减半。解码有 256 个元素，输出依然是两份矩阵，这些成本没有消失。

## 5. 内存模型对 shape 的启示

针对两份 M×N 输出、FP16 输入和 FP32 输出，假设每个矩阵从 HBM 仅读一次：

```text
普通输入：4*M*K + 4*K*N + 8*M*N bytes
预先打包、融合解码：2*M*K + 2*K*N + 8*M*N bytes
本次先物化打包、再融合计算：8*M*K + 8*K*N + 8*M*N bytes
```

这些只是最低逻辑数据量。实际缓存、复用、重复加载和写回会改变流量。

| M=N | K | 预打包的数据量比值：普通/候选 | 本次物化打包的数据量比值：普通/候选 |
|---:|---:|---:|---:|
| 16 | 32 | 1.500 | 0.600 |
| 64 | 32 | 1.200 | 0.750 |
| 512 | 32 | 1.030 | 0.944 |
| 4096 | 32 | 1.004 | 0.992 |
| 512 | 512 | 1.333 | 0.667 |
| 512 | 4096 | 1.800 | 0.529 |

因此仅把 M,N 拉大而 K 保持 32，会被两份输出的数据量淹没，几乎没有 HBM 流量优势。长 K 更有价值，但要保留分块解码及尺度处理，并避免把每块结果写到全局内存。单独 GEMM 后另起 unpack kernel 还会额外写、读一份中间 Z，增加 `8*M*N` 字节。

这里的 radix packed half 每个原始标量平均 8 bit，**比真正压缩的 MXFP4 元素 4 bit 更大**。不能把它与“压缩 FP4 存储、寄存器内反量化”的基线混淆。要比较训练收益，必须把读取压缩值、缩放、激活处理和梯度路径都算进去。

## 6. 接下来最值得硬件验证的顺序

1. 在同样 128-thread CTA 下，比较固定浮点解码和位模式解码。正确性覆盖 K32 全极值和随机输入，测端到端而非只数 HMMA。
2. 选择 M,N=64/256/512，K=32/512/4096，分别测试已打包、每次打包、融合解码三种边界。长 K 的两份输出在寄存器里累加。
3. 对齐每 32 项的 scale，单独统计可用 packing 值域覆盖率和退回路径成本。R256/K48 只在尺度兼容时测试。
4. 把 K4 原生 MMA 映射做成真正的数值探针，再评估七值 E2M1 子域。不要把 K4 精确性直接推广到完整 E2M1。
5. 最终与相同有效输出数量的 cuBLAS/适当压缩输入实现比较；这里两个朴素 WMMA 实现之间的优势不能替代这个基线。

## 7. 复现

`reproduce_compile.sh` 只编译和分析，不访问 GPU。它默认复用父工作区的私有 CUDA 12.8 工具链，可用 `V100_COST_TOOLCHAIN` 指向相同目录结构。用普通完整 CUDA 12.x 安装也可手工执行对应 `nvcc -c`、`cuobjdump --dump-sass` 命令。编译后执行：

```bash
python3 validate_magic_decode.py
python3 analyze_cost.py
```

不要把成功编译、零 CPU 错误或这份模型里的摊销周期写成 V100 实测成绩。
