# V100 数值模型仿真与 FP16 打包实验

日期：2026-11-22。

## 本次实际完成了什么

这次运行的是公开研究中的 **V100 Tensor Core 数值模型**，包含全局指数对齐、对齐时截断、未规范化的乘积、四项乘积与 C 的联合求和，以及最终向零舍入。它与普通 NumPy FP32 点积不同。

我们同时执行了作者未经修改的 MATLAB 模型和一个可逐项检查的 Python 整数位操作移植版：

| 验证 | 实际结果 |
| --- | --- |
| Python 移植版对照作者公开的 V100 硬件输出 | 5,000/5,000，FP32 位模式完全一致 |
| 原版模型在 GNU Octave 10.3.0 中对照同一硬件输出 | 5,000/5,000，FP32 位模式完全一致 |
| 原版模型对照移植版的打包和边界样例 | 885/885，FP32 位模式完全一致 |
| 六种受限打包方案在移植版中运行 | 30,940 个随机、常数极值及交替样例，全部正确 |
| 普通 IEEE FP32 顺序累加对照作者硬件输出 | 2,104/5,000 不同 |
| FP64 求和后一次 FP32 最近舍入对照作者硬件输出 | 1,885/5,000 不同 |

这些是 **CPU 上运行数值仿真的结果，以及对公开硬件回执的重验**。本次没有访问新的 V100 硬件，也没有测量 GPU 速度、功耗或训练收敛。

## 模型与普通 FP32 的具体区别

移植版 `v100_model.py` 采用整数表示有效数字，复现以下 V100 参数：

- 一个 BFMA 包含四项乘积与一个 FP32 累加输入 C。
- FP16 输入的两个有效数字相乘后，不预先规范化乘积。
- 所有乘积与 C 对齐到共同指数；被移出的位直接丢弃，不保留额外 guard/sticky 位。
- 对齐后的带符号整数一起相加，再规范化；FP32 输出向零舍入。
- 保留该分支支持的输入和输出子正规数。

它不是调用一次普通 FP32 GEMM 来冒充 V100。两个简单控制样例能展示差异：

| 表达式／输入 | V100 模型 | 普通 FP32 顺序求和 |
| --- | ---: | ---: |
| `2^-24 + 2^-24 + 1`，两个小项先算 | 1 | 1 + 2^-23 |
| `1 - 1 + 2^-24` | 0 | 2^-24 |

第一个例子里，小项在共同指数对齐时分别丢失；第二个例子里，随后发生抵消也不能找回已经丢失的位。

论文中的另一条控制样例也成功复现：同样是 `2.25 + 2^-23 + 2^-23`，若 2.25 来自 `1.5*1.5`，模型得到 `2.25+2^-22`；若来自 `1*2.25`，模型得到 2.25。这是“同样的数学乘积，但乘积内部指数表示不同”造成的差异。

## 打包方案的实际结果

以下 `q` 是整数。与 E2M1 元素建立联系时使用 `q=2*x`，因此 `q∈[-3,3]` 对应 `x∈{-1.5,-1,-0.5,0,0.5,1,1.5}`。它是完整 E2M1 数值域的一部分。

| 方案 | q 范围 | Radix | 每次解码前的 K | 样例数 | 解码错误 | 对齐时丢位的 BFMA 组 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 共享 B 的双输出 | -3…3 | 512 | 16 | 4,466 | 0 | 0 |
| 两路独立点积 | -1,0,1 | 128 | 16 | 4,258 | 0 | 0 |
| 两路独立点积 | -1,0,1 | 256 | 32 | 4,258 | 0 | 0 |
| 两路独立点积 | -3…3 | 512 | 4 | 6,578 | 0 | 0 |
| 两路独立点积 | -2…2 | 256 | 8 | 4,802 | 0 | 0 |
| 两路独立点积 | -3…3 | 256 | 4 | 6,578 | 0 | 0 |

每个方案包含 4,096 个随机样例，以及常数极值和交替符号样例。没有把这些有限测试称为“所有输入序列的穷举”；安全区间另有整数范围论证。

### 两路独立点积如何提取

令 `A=a0+R*a1`、`B=b0+R*b1`，则打包点积满足：

\[
Z=L+RC+R^2H,
\]

其中 `L=sum(a0*b0)`、`H=sum(a1*b1)` 是所需输出，`C=sum(a0*b1+a1*b0)` 是交叉项。

```text
H = round(Z/R²)
remainder = Z - R²*H
C = round(remainder/R)
L = remainder - R*C
```

交叉项没有消失，而是被分离后丢弃。

### 为什么 V100 的特殊舍入没有破坏这些安全区间

这些候选都使用精确的 FP16 整数编码。它们的整数乘积和任意部分和落在 FP32 精确整数范围内，共同指数对齐的最小单位也不大于 1。因此在安全区间内不存在可被截断的非零位；最终向零舍入也不改变结果。实际 trace 显示六种候选全部没有对齐丢位。

两个有代表性的范围：

- **三值、R256、K32**：操作数最大 257，`|L|,|H|≤32`、`|C|≤64`，任意部分和不超过 2,113,568。
- **q[-3,3]、R256、K4**：操作数最大 771，`|L|,|H|≤36`、`|C|≤72`，`256*72+36=18468<32768`，任意部分和不超过 2,377,764。这适合进一步探索 sm70 的四项归约粒度。

对长 K，必须在安全块边界解码，然后分别累计两路结果。不能把打包累加器无限延长；解码、额外寄存器及数据重排的成本仍可能消耗理论上的收益。

## 仿真明确排除的扩张

### q[-3,3]、R512 从 K4 延长到 K8

令两个打包输入均为：

```text
[1537,1536,1536,1536,1536,1536,1536,1536]
```

对应高位输入全为 3，低位输入只有第一项为 1。期望两个点积为 `(1,72)`。精确打包和为 **18,877,441**，V100 模型得到 **18,877,440**，解码得到 `(0,72)`。这是越过有效精度边界后低路丢失的具体反例。

### 三值、R1024、K16

输入前 3 项为 1025，其余 13 项为 1024，两边相同：

| 计算 | 打包和 | 解码得到的低路 |
| --- | ---: | ---: |
| 精确整数 | 16,783,363 | 3 |
| V100 数值模型 | 16,783,362 | 2 |
| 普通 IEEE FP32 顺序累加 | 16,783,364 | 4 |

两种浮点路径都不再精确，而且错误方向不同。这个例子说明采用 V100 模型会实质改变不安全区间的结果。

### 完整 E2M1 标量 lookup 仍无法直接累加

对完整 15 个数值的 E2M1 域，`a0+128*a1` 与共享 `b` 相乘，全部 3,375 个标量组合依旧得到 849 个无歧义的输出 key。V100 模型没有推翻这个标量阳性。

但长度 2 时仍出现精确碰撞：同一个 `B=[8,1]`，`A0=[8,0],A1=[0,0]` 的目标为 `(64,0)`，而 `A0=[-8,0],A1=[0,1]` 的目标为 `(-64,1)`；打包点积均为 64。原版模型与移植版均确认碰撞。该失败来自编码本身，不能通过模拟更精确的舍入来修复。

## 覆盖边界与仍需完成的工作

公开的 5,000 个硬件样例全部是有限值，A/B 共 40,000 个输入中没有零和 FP16 子正规数。A 的无偏指数范围为 -13…1，B 为 -14…1；C 和 D 也没有子正规数。因此，5,000/5,000 一致不能单独证明全部极端指数和特殊值处理都正确。

我们额外运行了 FP16 最小子正规数、FP16 最大有限值及抵消、FP32 子正规累加输入、FP32 最大有限累加输入、论文舍入样例和打包边界样例，并在原版 Octave 模型中交叉验证。它们验证的是实现一致性及模型行为，不能补成新的硬件实测。

Python 移植只实现有限 FP16 A/B 与 FP32 C/D 的分支，不实现 FP16 输出、其它 GPU 架构或任意 NaN payload 规则。大矩阵的调用顺序遵循作者 GEMM 驱动；真实 WMMA/cuBLAS 可能采用不同的较大归约顺序。

仿真没有涉及寄存器分配、指令调度、访存、SM 占用、功耗或训练。结果支持继续实现安全区间内的打包内核，并反对“浮点打包一概不可能”的说法；它还不能证明完整 MXFP4 训练加速或优于优化后的 FP16 GEMM。
