## 1. 最直接的双侧打包正例：两路独立三值点积

令 a0、a1、b0、b1 的每个元素都属于 {-1,0,1}，各有 K=32 项。分别打包：

```text
A = a0 + 256*a1
B = b0 + 256*b1
Z = sum(A*B) = L + 256*C + 65536*H
L = sum(a0*b0)
H = sum(a1*b1)
C = sum(a0*b1 + a1*b0)
```

两个目标 L 和 H 是独立点积；中间交叉项 C 可以提取后舍弃：

```text
H = round(Z / 65536)
r = Z - 65536*H
C = round(r / 256)
L = r - 256*C
```

这并非忽略交叉项。它明确为交叉项保留一段数值空间：|L|、|H| <= 32，|C| <= 64；|256*C+L| <= 16416 < 32768，|L| < 128。FP16 输入最大绝对值只有 257，全部是可精确表示的整数。任意部分累加的绝对值不超过 32*257^2 = 2,113,568，小于 FP32 精确整数范围 2^24。

实际 CPU 检查：81 个标量四元组，及包含全部合法结果的 545,025 个整数 (L,C,H) 系数组合，均零错误。穷举的是保守结果集合，结合范围证明覆盖合法输入；并未声称枚举 81^32 个输入序列。R=128、K=16 的较小版本也通过 70,785 个系数组合。

这是三值算术，不是完整 E2M1 的所有取值。K=32 与 MX 块长度一致，并不使它自动成为完整 MXFP4 算子。实际 V100 的正确性与速度仍要运行探针。

## 2. 更宽的 E2M1 子集：共享右矩阵的两路输出

E2M1 数值 x 乘 2 后可用整数 q 表示。本构造只用 q in {-3,-2,-1,0,1,2,3}，对应 x in {0,+/-0.5,+/-1,+/-1.5}。

```text
P = a0 + 512*a1
Z = sum(P*b), K=16
high = round(Z/512)
low = Z - 512*high
```

FP16 打包值最大 1539；低位点积最大 144，小于半基数 256；任意打包点积部分和最大 73,872，可以精确放入 FP32。原 E2M1 乘积是解出的 q 点积除以 4，再应用相应 MX 块尺度。

343 个标量三元组和 83,521 个保守输出对穷举均为零错误。这里的两路结果共享 b，与第一种双侧打包的独立输入条件不同。

长 K 可在每 16 项后解包，再分别累加两个结果；CUDA 源码提供了这个候选。但频繁解包、额外指令及数据处理可能吃掉减少 Tensor Core 工作量的好处，不能仅凭数学构造推算加速。

## 3. 完整 E2M1：单次乘法有映射，累加后出现碰撞

完整 E2M1 的 q 数值集合为 {0,+/-1,+/-2,+/-3,+/-4,+/-6,+/-8,+/-12}。正负零按同一数值处理，因此是 15 个数值，未要求保留零符号位。

P=a0+128*a1 与共享 b 相乘时，225 个打包输入全部 FP16 精确；3,375 个输入三元组产生 849 个结果 key，没有“相同结果却要求不同目标乘积”的冲突。这允许查表解码。普通 nearest-radix 解码则有 300 个错误，不能混用二者。

但只累加两项就出现精确碰撞，同一个 B=[8,1]：

| A0 | A1 | 正确双输出 | 打包点积 Z |
| --- | --- | --- | --- |
| [8,0] | [0,0] | (64,0) | 64 |
| [-8,0] | [0,1] | (-64,1) | -64+128=64 |

全部输入和运算都精确，单凭 Z=64 已经不能区分两个答案。补零到 WMMA 的 K=16 不会消除这个碰撞。结论只排除这一固定编码依靠 Z 单独恢复两个点积，不排除其他编码、额外旁信息、稀疏算法或近似方法。

增大基数又会碰到输入精度问题：R=512 时，(a0,a1)=(0,12) 与 (1,12) 的目标打包值分别是 6144 和 6145，但 FP16 把二者都表示成 6144。

随机正确不等于全域正确：受限 q[-3,3]/R512 的 4,096 个随机样本在 K32、K64、K128 上都没有解码错误，然而 K32 全取 a0=b=3、a1=0 时，目标 (288,0) 会被解成 (-224,1)。因此探针同时保留极值、碰撞和随机用例。

## 4. 真实 V100 探针如何运行

在目标机现成、支持 sm_70 的 CUDA 12.x 开发环境中：

```bash
cd gpu_probe
./run.sh --device 0
```

也可先运行：

```bash
./run.sh --device 0 --correctness-only
./run.sh --device 0 --benchmark-only --warmup 10 --iters 100
```

程序默认核对 GPU 名称和 compute capability，非 V100 会拒绝；显式允许其他卡时仍标记 actual_V100=false。脚本记录 GPU UUID、驱动、CUDA/cuBLAS 版本、前后温度与利用率、源码/二进制哈希和 JSONL 结果。它不停止服务、不改时钟、不安装依赖。选择空闲卡才能解释性能结果。

正确性包括 240 个 shared-RHS WMMA 配置、双侧标量穷举、K16/K32 三值正例和完整 E2M1 碰撞。理论保证的正例若失败会终止；故意超范围的用例报告错误数量，不会把它们误读成“一切方案均失败”。

性能对比输出规模严格相同：基线是一次 2M 行的 cuBLAS GEMM；候选是打包后一次 M 行 GEMM再解出两份输出。分别记录 compute、pack、unpack，以及 pack+compute+unpack 总时间。长 K 另有每 16 项解码的朴素 WMMA 候选，它不是优化后的微内核，不能用它输给 cuBLAS 来证明任何优化实现都无效。

所有输出与 cuBLAS 逐元素比较，另有 32 项精确整数参考。任何 benchmark 正确性失败都会退出。有效 FLOP/s 按相同逻辑工作量计数，不表示芯片获得了原生 FP4 运算单元。当前实现未加入实际块尺度变化、量化器、训练反向、优化器或收敛测量。

## 5. Soft-BF16-V100 仓库评价

固定版本是有实际技巧的兼容与加速原型。作者完成了范围规约、幂次缩放、FP16 打包、cuBLAS 调用、缩放恢复、scratch 处理和部分 FP32 修复。主 GEMM 调用 cublasGemmEx，不能把整个 Tensor Core 内核都归为作者自研。

代码明确有一阶 autograd backward，所以“训练纯没用”“只能 LoRA”缺少证据。二维矩阵支持选择性坏行/列修复，但超过阈值仍会整体回退；batched 路径的 unsafe 情况会整批回退。

该版本公开树没有配套 README、自动测试、CI 或完整 benchmark 脚本。源码和提交中有作者性能数字，但不足以证明对话声称的总体五六倍、80–90 TFLOPS 或训练慢七八倍。未复现的数字在 audit/audit-notes.md 中明确标作作者声称。

“幂次缩放保证所有允许 BF16 输入的尾数无损”也过强。CPU IEEE 模型显示：一行最大值为 1，另一个精确 BF16 数 x=129*2^-37，会通过默认 guard；缩放到 FP16 再还原由 9.38598532229662e-10 变为 9.313225746154785e-10，误差约 -0.7752%。这是 pack 的反例，不等于实际整个模型有相同比例的误差，也未在 GPU 上复现。另有 SDPA guard 允许极小值归零的反例。

## 6. 尚不能作出的结论

本包没有 V100 正确性回执、速度、能耗或训练损失曲线。尚未得到完整 E2M1/MXFP4 的通用高效点积编码，也没有证明任何其他编码都不可能。

若继续追求训练收益，需要在实卡上先确认算术路径，再测相同输出规模下包含全部转换的耗时，最后查看真实权重、激活和梯度中可满足受限域条件的比例。数据压缩节省显存/带宽，与打包算术减少实际乘加工作量，是两个分别需要验证的收益来源。
